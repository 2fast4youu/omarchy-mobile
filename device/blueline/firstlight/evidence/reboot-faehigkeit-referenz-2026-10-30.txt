# Prüfstein Schritt 0: kann die Referenz-Shell von sich aus in den Bootloader?
# Aufnahme 2026-10-30, nur lesend per Telnet 172.16.42.1:23, Uptime dabei 58014 s.
# Anlass: Schritt 0 des FLASH-BEREIT-Blocks nannte 'reboot bootloader' als
# Telnet-Befehl. Das Wort stammt aus fastboot ('fastboot reboot bootloader'),
# in einer Busybox-Shell ist es ein Argument an busybox reboot.

BusyBox v1.38.0 (2026-10-25 19:58:26 UTC) multi-call binary.

$ busybox --list | grep -E 'reboot|power|halt|rest'
halt
poweroff
reboot

$ ls -l /sbin/reboot
lrwxrwxrwx 1 0 0 12 Jan 1 00:00 /sbin/reboot -> /bin/busybox

# Der entscheidende Messwert: das Wort 'bootloader' kommt im Binary nicht vor.
# Beide Leser, unabhängig voneinander, beide 0:
$ strings /bin/busybox | grep -xc bootloader
0
$ grep -c bootloader /bin/busybox
0

# Ein Argument, das im Binary nirgends steht, kann kein RESTART2-Grund werden:
# busybox reboot kennt -d SEC und -f, weiter nichts. 'reboot bootloader' ist
# damit ein Warmboot ins aktuelle Slot = die Referenz startet sich selbst, und
# run-flash-observe.sh Zeile 79 ('kein Fastboot-Geraet') stiege erneut aus.
#
# Es gibt kein Ausweichwerkzeug in diesem Initramfs:
$ which restart2 reboot-to fastbootd systemctl
(leer)
$ ls /system/bin/reboot
ls: /system/bin/reboot: No such file or directory
# (restart2, unser 162-KiB-RESTART2-Helfer aus firstlight/, steckt nur in
#  unseren eigenen Bildern v0m+, nicht im Referenz-Initramfs.)

# Beschluss aus der Messung: Schritt 0 ist ein Tastenvorgang, kein Befehl.
# Gregor haelt LEISER gedrueckt, waehrend 'reboot' in der Shell laeuft, bis
# FASTBOOT MODE im Display steht. Das ist derselbe Halter, der im Dunkel-Fall
# laengst eingeplant war - nur jetzt an seinem sicheren Ort, mit laufendem
# Kernel und wachem Beobachter statt im Ernstfall.
